# Игровой Master Server

Этот проект — сервер для игрового клиента. Он написан на **Node.js и TypeScript**:

- исходный код, который редактируют разработчики, находится в `src/`;
- команда сборки превращает TypeScript в JavaScript и записывает результат в `dist/`;
- это **не Java-проект**: папка `dist/` содержит собранный JavaScript, а не Java-код.

Эта инструкция описывает установку и локальный тестовый запуск. Наличие README не означает, что сервер уже безопасен для открытого доступа в Интернет: важные ограничения перечислены в разделе [Безопасность](#безопасность-и-что-важно-знать).

## Что понадобится

Установите и запустите следующие программы:

1. **Node.js 20 или новее** и npm. npm обычно устанавливается вместе с Node.js. Проверить установку можно командами `node --version` и `npm --version`.
2. **MongoDB** — база, в которой сервер хранит аккаунты, игровые сохранения, баны, подарки и другие данные.
3. **Redis** — служба, которую сервер использует для обмена WebSocket-событиями. Redis нужен даже при запуске одного процесса.
4. **Git** — чтобы скачать проект с GitHub.

MongoDB и Redis должны быть доступны на компьютере или сервере до запуска приложения. Их установка зависит от операционной системы и способа размещения; для первого теста можно запустить их локально. Если используете облачные сервисы, возьмите адреса подключения в их панели управления и храните пароли только в локальном `.env`.

## Скачать и установить проект

После публикации замените `<URL_РЕПОЗИТОРИЯ>` на адрес GitHub-репозитория:

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd <ПАПКА_ПРОЕКТА>
npm ci
```

`npm ci` устанавливает зависимости, перечисленные в `package-lock.json`. Если при разработке изменили зависимости в `package.json`, сначала обновите lock-файл командой `npm install` и включите оба файла в коммит.

## Создать локальную конфигурацию

Скопируйте пример настроек в `.env`.

**Windows PowerShell:**

```powershell
Copy-Item .env.example .env
```

**Linux или macOS:**

```bash
cp .env.example .env
```

Откройте `.env` в редакторе и заполните значения. Это локальный файл вашей машины: **не загружайте его на GitHub и не отправляйте другим людям**. `.gitignore` настроен исключать `.env`, но перед публикацией всё равно проверяйте список файлов, которые собираетесь добавить в Git.

Пример локальных адресов MongoDB и Redis (если обе службы запущены на том же компьютере):

```dotenv
MONGO_URI=mongodb://127.0.0.1:27017/YOUR_DATABASE_NAME
REDIS_URL=redis://127.0.0.1:6379
```

Замените `YOUR_DATABASE_NAME` на имя базы, например `game_server`. Для облачной базы используйте URI, выданный провайдером, вместо локального адреса.

### Настройки `.env`

| Переменная | Что указать |
| --- | --- |
| `PORT` | Порт HTTP API и WebSocket-сервера. По умолчанию `3000`. |
| `WS_HOST` | Адрес WebSocket, который сервер сообщает игровому клиенту. Укажите доступный клиенту адрес вместе с `ws://` или `wss://`; замените `YOUR_SERVER_HOST`. |
| `WS_PORT` | Порт WebSocket, который сообщается клиенту. По умолчанию `8000`. Убедитесь, что этот порт доступен клиентам и настроен в сетевом экране или прокси. |
| `CLIENT_VISIBLE_NAME` | Имя сервера, отображаемое клиенту. |
| `MASTER_ENCRYPTION_KEY` | Секрет сервера для AES-256-CBC. Укажите случайную строку не короче 32 UTF-8 байт. Приложение преобразует ее в AES-ключ через SHA-256. |
| `CLIENT_ENCRYPTION_KEY` | Ключ игрового протокола, который сервер возвращает клиенту. Он должен совпадать с настройкой, ожидаемой вашим клиентом; не путайте его с `MASTER_ENCRYPTION_KEY`. |
| `MONGO_URI` | Адрес подключения к MongoDB. При локальном запуске обычно начинается с `mongodb://127.0.0.1:27017/`. |
| `REDIS_URL` | Адрес подключения к Redis. Для локального запуска используется `redis://127.0.0.1:6379`. |

`MASTER_ENCRYPTION_KEY` и `CLIENT_ENCRYPTION_KEY` — разные настройки: не используйте одно значение для обеих. Не публикуйте ключи и пароли в README, исходном коде, скриншотах или публичных сообщениях. Если в URI базы есть пароль со специальными символами, закодируйте его для URI. Для размещения в Интернете храните секреты в настройках окружения хостинга, а не в `.env` репозитория.

### Создание секрета для `MASTER_ENCRYPTION_KEY`

Для локального теста можно сгенерировать случайный секрет командой Node.js:

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"
```

Скопируйте результат в локальный `.env` после `MASTER_ENCRYPTION_KEY=`. Не отправляйте его в чат и не добавляйте в Git. Сервер получает из этого секрета AES-ключ через SHA-256; сам секрет должен оставаться приватным.

## Собрать и запустить

Откройте терминал в папке проекта. Каждый раз после изменения TypeScript соберите проект:

```bash
npm run build
```

После успешной сборки запустите один серверный процесс:

```bash
npm start
```

Сначала приложение проверит настройки и подключится к MongoDB и Redis. Только после успешного подключения оно начнет слушать порт `PORT`. Оставьте окно терминала открытым, пока сервер работает; остановить его можно сочетанием `Ctrl+C`.

HTTP и WebSocket обслуживаются одним listener-ом и фактически используют порт `PORT`. При этом `WS_HOST` и `WS_PORT` — адрес и порт, которые сервер сообщает игровому клиенту. Для простого теста задайте одинаковые `PORT` и `WS_PORT`. Если они различаются, настройте прокси или перенаправление порта, чтобы опубликованный `WS_PORT` вел на фактический `PORT`.

Для теста в локальной сети укажите адрес компьютера, на котором работает сервер и который доступен игровому клиенту. Для публичного сервера обычно нужны доменное имя, открытые/перенаправленные порты и TLS reverse proxy; клиентское соединение должно использовать `wss://`.

## Какие функции есть

Сервер предоставляет HTTP API для клиента и отдельное WebSocket-соединение для игровых сообщений. Основные группы маршрутов:

| Адрес | Для чего используется |
| --- | --- |
| `GET /settings/client`, `GET /settings/2.0/client` | Выдать клиенту настройки сервера. |
| `GET /time` | Вернуть текущее серверное время. |
| `POST /auth/login`, `POST /auth/register` | Вход и регистрация аккаунта. |
| `POST /auth/save_2.0`, `POST /auth/load_2.0`, `POST /auth/name_2.0` | Сохранение, загрузка данных и обновление имени. |
| `POST /promocode` | Обработка промокода; сейчас это тестовая логика. |
| `POST /purchases/validate/validate` | Обработка покупки; настоящей проверки платежа пока нет. Повтор `validate` — текущее legacy-поведение маршрута. |
| `GET /search/...` | Старые поисковые endpoints с фиксированным PIN. |
| `/moderation/...` | Просмотр и изменение данных игроков, подарков, банов и мутов. |
| `POST /report/ban` | Создать запись о бане через report endpoint. |

Чтобы посмотреть точный формат запросов и ответов, изучайте соответствующие файлы в `src/routes/`. Endpoint-ы модерации особенно важно не выставлять в Интернет без настройки защиты.

### Дополнительные команды

```bash
npm run typecheck  # проверить типы TypeScript, не запуская сервер
npm test           # сейчас тоже запускает проверку типов, а не игровые тесты
npm run clean      # удалить собранную папку dist
npm run cluster    # запустить три worker-процесса
```

Для обычного тестового запуска используйте `npm start`. `npm run cluster` нужен только для нескольких worker-процессов; не запускайте оба варианта одновременно на одном порту. В режиме кластера каждый worker подключается к MongoDB и Redis.

## Что находится в проекте

- `src/` — TypeScript-код сервера, HTTP-маршрутов, WebSocket, схем MongoDB и утилит.
- `dist/` — скомпилированный JavaScript; создается командой `npm run build`, вручную редактировать его не нужно.
- `.env.example` — пример настроек с плейсхолдерами, не секретный конфигурационный файл.
- `package.json` и `package-lock.json` — команды и версии npm-зависимостей.
- `sdsart.bat` — вспомогательный Windows-файл запуска `npm start`.
- `src/database/data/` — файлы legacy JSON-хранилища; это не замена MongoDB и Redis.

Основные технологии: Node.js, TypeScript, Express, `ws`, MongoDB/Mongoose, Redis, Helmet, CORS, Morgan и dotenv.

## Если запуск не удался

- **Ошибка про `MASTER_ENCRYPTION_KEY`:** в `.env` должна быть строка не короче 32 UTF-8 байт. Не вставляйте кавычки внутрь значения и не публикуйте сам ключ.
- **Ошибка про `YOUR_...`:** откройте `.env`, заполните обязательные адреса, имя и ключ клиента, затем перезапустите сервер.
- **Ошибка подключения MongoDB:** убедитесь, что MongoDB запущена, URI и имя базы указаны верно, а для удаленной базы разрешено подключение с вашего сервера.
- **Ошибка подключения Redis:** убедитесь, что Redis запущен, URL верен и адрес доступен приложению.
- **Клиент не подключается:** проверьте `WS_HOST`, `WS_PORT`, настройки firewall/router/reverse proxy и совпадение адреса с тем, который клиент реально может достичь.
- **Изменения TypeScript не появились:** повторно выполните `npm run build`, затем перезапустите сервер.

Не отправляйте в публичные обсуждения полный `.env`, URI с паролем или логи, содержащие личные данные.

## Безопасность и что важно знать

В проекте есть старое и тестовое поведение. До публичного развертывания нужно провести отдельную проверку и закрыть как минимум следующие вопросы:

- Старые search endpoints используют фиксированный PIN. Он оставлен для совместимости, но не обеспечивает реальную защиту.
- Пароли аккаунтов хранятся и сравниваются в открытом виде. Не используйте реальные или повторно используемые пароли.
- Для маршрутов модерации нет полноценной аутентификации и проверки прав администратора. Ограничьте доступ на уровне сети.
- Проверка покупок и промокоды являются заглушками, а не реальной проверкой оплаты и прав.
- CORS разрешителен; для развертывания его следует ограничить нужными клиентами.
- AES-CBC не заменяет HTTPS/WSS, надежную аутентификацию и авторизацию.

Не открывайте этот сервер для публичного использования, пока эти ограничения не устранены. Если настоящий секрет когда-либо попадал в Git или был опубликован, считайте его раскрытым и замените.
